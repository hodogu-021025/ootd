# 10 화면과 데이터 연결

> 화면이 데이터를 어떻게 읽고 저장하는지 정리합니다. 데이터 구조는 05 데이터 정의서, 화면 구현은 09 문서를 봅니다.

---

## 10.1. 데이터를 나누는 기준

| 데이터 | 어디에 두는가 | 이유 |
|---|---|---|
| 의류·카테고리·사진 등록표 | `src/mocks`의 기초 데이터 | 바뀌지 않는 기본 값 |
| 의류(재고 포함)·장바구니·주문·좋아요·최근 검색어·재입고 알림 | localStorage + Context | 여러 화면이 함께 쓰고, 새로고침해도 남아야 한다 |
| 검색어·필터·정렬 | 주소 쿼리 | 새로고침·뒤로 가기에도 같은 결과를 보여 주기 위해 |
| 선택 사이즈·입력 중인 값·열림 여부 | 화면의 state | 그 화면에서만 쓰고 저장할 필요가 없다 |

## 10.2. Context 구성 — `src/main.jsx`

```
ProductsProvider          의류 + 사이즈별 재고
  └ CartProvider          장바구니 (의류 정보를 붙이려고 Products 안에 둔다)
     └ OrdersProvider     주문 내역
        └ WishlistProvider        좋아요
           └ RestockAlertsProvider 재입고 알림 신청
              └ App
```

| Context | 저장 키 | 주요 값·함수 |
|---|---|---|
| `ProductsContext` | `ootd_products` | `products`, `getProduct`, `getStock`, `getProductStock`, `prepareStockDecrease`, `increaseStock`, `addProduct`, `updateProduct`, `deleteProduct`, `resetStorage` |
| `CartContext` | `ootd_cart` | `items`, `count`, `error`, `addItem`, `updateQuantity`, `removeItem`, `prepareRemoveItems`, `resetStorage` |
| `OrdersContext` | `ootd_orders` | `orders`, `prepareOrder`, `cancelOrder`, `resetStorage` |
| `WishlistContext` | `ootd_wishlist` | `likedIds`, `isLiked`, `toggleLike`, `resetStorage` |
| `RestockAlertsContext` | `ootd_restock_alerts` | `alerts`, `isRequested`, `requestAlert`, `removeAlert`, `markNotified`, `resetStorage` |

최근 검색어(`ootd_recent_searches`)는 검색창에서만 쓰므로 `components/SearchBox.jsx` 안에서 직접 읽고 쓴다.

모든 Context는 `storageBroken`(저장 데이터를 읽지 못함)을 함께 내보내고, `StorageNotice`가 이를 모아 안내한다.

## 10.3. 저장 도우미 — `src/utils/storage.js`

| 함수 | 역할 |
|---|---|
| `readStorage(key, isValid)` | 읽고 JSON 변환·구조 검사. `{ value, broken }`을 돌려준다 |
| `writeStorage(key, value)` | 하나를 저장한다. 성공 여부를 돌려준다 |
| `writeStorageAll(entries)` | 여러 키를 한 번에 저장한다. 도중에 실패하면 이미 쓴 값을 되돌린다 |
| `clearStorage(key)` | 사용자가 초기화를 확인했을 때만 지운다 |

`utils/price.js`는 판매 가격과 배송비(0원), `utils/sort.js`는 정렬 기준과 무작위 순서표를 담당한다.

## 10.4. 화면별 연결

| 화면 | 읽기 | 쓰기 |
|---|---|---|
| S-01 홈 | 없음(코디 소개는 화면 안의 상수) | 없음 |
| S-02 목록 | `products`, 카테고리, 주소 조건, 최근 검색어, `isLiked` | 주소 조건, 최근 검색어, `toggleLike` |
| S-03 상세 | `getProduct`, `getProductStock`, `items`(담긴 수량), `isLiked`, `isRequested` | `addItem`, `toggleLike`, `requestAlert` |
| S-04 장바구니 | `items`, `getStock` | `updateQuantity`, `removeItem` |
| S-05 주문서 | `items`, `getStock` | `prepareOrder` + `prepareRemoveItems` + `prepareStockDecrease` → `writeStorageAll` |
| S-06 주문 완료 | `orders`에서 주소의 주문 번호로 찾기 | 없음 |
| S-07 주문 내역 | `orders`, `getProduct`(사진) | `cancelOrder`, `increaseStock` |
| S-08 좋아요 목록 | `likedIds`, `getProduct` | `toggleLike` |
| S-09 관리자 | `products` | `addProduct`, `updateProduct`, `deleteProduct` |
| S-11 LISTS | `likedIds`, `alerts`, `getProduct`(미리 보기) | 없음 |
| S-12 재입고 알림 목록 | `alerts`, `getProduct` | `removeAlert` |
| 공통 헤더 | `count` | 없음 |
| 공통 팝업 | `alerts`, `products`(재고·재입고 일시) | `markNotified` |

## 10.5. 저장 흐름

### 기본 흐름

1. 다음 값을 새로 만든다(기존 배열·객체를 직접 바꾸지 않는다).
2. 먼저 저장한다.
3. 성공하면 화면 상태를 바꾸고 안내한다.
4. 실패하면 이전 상태를 유지하고 실패를 안내한다.

### 주문 (F-12) — 한 번에 저장

1. 재고 차감·주문 추가·장바구니 비우기의 저장 내용을 각각 **계산만** 한다.
2. `writeStorageAll`로 세 키를 잇달아 쓴다. 도중에 실패하면 이미 쓴 키를 되돌린다.
3. 저장에 성공했을 때만 세 Context의 상태를 반영하고 주문 완료 화면으로 이동한다.

### 재고가 움직이는 경로

| 경로 | 처리 |
|---|---|
| 주문 (F-12) | 주문 수량만큼 차감 |
| 주문 취소 (F-18) | 주문 수량만큼 복원. 삭제된 의류·없어진 사이즈는 제외 |
| 관리자 수정·재입고 (F-24·F-25) | 입력한 수량으로 바꾸기 |

어느 경로든 재고가 **0에서 1 이상**이 되면 그 사이즈의 재입고 일시를 기록하고, 이 값이 재입고 알림 팝업(F-29)의 기준이 된다.

## 10.6. 불러오기·복원 (F-14)

1. 화면을 열 때 각 키를 읽고 구조를 검사한다.
2. 키가 없으면 기본값으로 시작한다(의류는 mock 데이터).
3. 검사에 실패하면 **원본을 지우지 않고** 그 데이터만 '읽지 못함'으로 표시한다.
4. 안내 줄의 초기화를 선택하고 확인해야만 해당 키를 지우고 기본값으로 시작한다.
5. 그동안 저장이 필요한 동작은 막고, 읽기만 하는 화면은 그대로 쓸 수 있다.

## 10.7. 데이터가 바뀔 때의 화면 반영

| 바뀐 데이터 | 함께 바뀌는 화면 |
|---|---|
| 장바구니 | 헤더 수량, 장바구니, 주문서, 상세의 담기 가능 수량 |
| 재고 | 상세의 사이즈 상태, 장바구니 경고, 관리자 목록 상태, 재입고 알림 팝업 |
| 의류(등록·수정·삭제) | 목록·상세·관리자 목록, 장바구니의 구매 불가 표시 |
| 주문 | 주문 내역, 주문 완료 화면 |
| 좋아요 | 목록·상세의 하트, 좋아요 목록 |
| 재입고 알림 | 상세의 신청 버튼, 재입고 알림 목록, 팝업 |

Context가 값을 내려 주므로 화면마다 따로 복사해 두지 않는다. 같은 데이터를 두 곳에서 관리하면 화면이 어긋나기 때문이다.
